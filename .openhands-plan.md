## 1. Befund (evidenzbasiert, aus reiner Lektüre — keine Codeänderung)

1. **Qualitäts-Gate ist vorhanden, aber nicht ausgeführt.** `package.json` kennt `check` (`tsc --noEmit`),
   `test` (`vitest run`), `build` (`vite + esbuild`), `validate` (= check + test + build + `git diff --check`).
   Es gibt **kein `lint`-Script** (nur `format` via Prettier). `node_modules/` fehlt im Workspace —
   Tests/Build brauchen zuerst `pnpm install --frozen-lockfile` (per AGENTS.md, Node v24 im Container,
   nur „Unsupported engine"-Warnung).
2. **Doku driftet gegen den Code.** `AGENTS.md` sagt „169 Passed / 4 skipped", `docs/SPRINT-STATUS.md`
   dokumentiert für Sprint 100 dagegen **811 Passed / 4 skipped**. 112 Testdateien liegen in
   `server/`, `client/src/`, `tests/` (`vitest.config.ts` deckt sie ab).
3. **`.env.example` ist unvollständig.** 33 von 47 im Code referenzierten `process.env.*`-Variablen
   (u. a. `JWT_SECRET`, `OPENROUTER_BASE_URL`, `PUBLIC_BASE_URL`, `PORT`, `PROVIDER_GUARDIAN_INTERVAL_MS`,
   `PROVIDER_FALLBACK_ORDER`, `AGENT_OPERATOR_EMAIL`, `OLLAMA_*`, `VITE_APP_ID`, `GEMINI_MODELS`/`GROQ_MODELS`/`HF_MODEL`)
   fehlen in `.env.example`. Das erschwert lokale Einrichtung (AGENTS.md beschreibt die E2E-Prüfung mit
   `JWT_SECRET` + Mock-Basis-URL, die im Beispiel nicht auftaucht). **Werte werden in keinem Schritt
   gesetzt (nur Platzhalter/Namen) — keine Secrets berühren, nur `.env.example`.**
4. **Modellrouten-Befund (kein Eingriff geplant).** Der Leitprompt nennt eine einzige Route aus
   `config/local-llm.env` (`LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY`/`LLM_OFFLINE`) und
   `docs/LOCAL-OFFLINE-LLM.md`. Beides existiert im Repo nicht und wird im Code nirgends referenziert.
   Stattdessen fährt das Projekt eine Mehr-Anbieter-Kette **OpenRouter → Groq → Gemini**
   (Hugging Face nur mit Einwilligung) in `server/agent-engine.ts` (`callWithProviderChain`),
   URLs zentral in `server/provider-endpoints.ts`, Env-Keys `OPENROUTER_API_KEY`, `GROQ_API_KEY`,
   `GEMINI_API_KEY`, `HF_TOKEN` (`.env.example` hat sie). Eine Umstellung auf eine lokale Einzelroute
   wäre ein großer, riskanter Systemeingriff (Provider-Guardian, Failover-Tests in
   `server/agent-engine.test.ts`, Live-Testschalter `RUN_LIVE_OPENROUTER_CHECK`) und gehört **nicht** in
   einen Wache-Sprint. **Annahme (konservativ):** bestehende Kette bleibt unangetastet; die Abweichung
   wird nur als offene Entscheidung dokumentiert (Abschnitt 4).
5. **Git-Status:** Arbeitsbaum sauber bis auf untracked Skill-Dateien unter `.agents/skills/` (vom
   Workflow bereitgestellt, nicht anfassen). Keine Nutzeränderungen im Produktcode.

## 2. Ziel des Sprints

Das Projekt „funktionsfähig halten": erst messen (Gate laufen lassen), dann nur echte,
kleine, nachvollziehbare Verbesserungen umsetzen. Keine neuen Abhängigkeiten, keine neuen
Provider/Endpunkte, keine Verhaltensänderung am Chat-/Provider-Pfad.

## 3. Umsetzungsplan (3 Änderungen, in dieser Reihenfolge)

1. **Gate verifizieren & Doku-Befund korrigieren** — Befund 1+2.
   - `pnpm install --frozen-lockfile`, dann `pnpm check`, `pnpm test`, `pnpm build` (oder `pnpm validate`)
     ausführen und das tatsächliche Ergebnis (Passed/Skipped-Zahl) ins Protokoll schreiben.
   - `AGENTS.md`-Zeile zur Testzahl auf den **gemessenen** Wert aktualisieren (nicht raten —
     nur nach grünem Lauf). Betroffene Datei: `AGENTS.md`.
   - Risiko: niedrig (Doku). Abbruch, wenn der Gate-Lauf rot ist → dann stattdessen nur den
     Fehler protokollieren und keine weiteren Änderungen vornehmen (Wache-Prinzip).
2. **`.env.example` vervollständigen (nur Namen + Platzhalter)** — Befund 3.
   - Fehlende öffentliche Konfigurationsvariablen aus `server/env.ts`, `server/provider-endpoints.ts`,
     `server/_core/index.ts`, `server/_core/googleAuth.ts` (u. a. `JWT_SECRET`, `OPENROUTER_BASE_URL`,
     `PUBLIC_BASE_URL`, `PORT`, `PROVIDER_*`) ergänzen, ohne je einen echten Wert einzutragen.
     Secret-Warnung aus dem Leitprompt bleibt: nur Platzhalter wie `…=`, kein Wert.
   - Optionale/Live-Schalter (`RUN_LIVE_*`, `STRIPE_*`) als kommentierte oder klar optionale
     Einträge kennzeichnen, falls `.env.example`-Stil (Header-Kommentare) dies vorsieht.
   - Betroffene Datei: `.env.example`. Risiko: niedrig (keine Laufzeitwirkung; Datei ist Beispiel).
   - Prüfung: `grep`-Abgleich Env-Namen Code ↔ Beispiel wie im Befund (nur Namen, keine Werte).
3. **Offline-/Mock-E2E-Doku-Angleich ohne Parser-Umbau** — optional, nur falls 1+2 grün und klein bleiben.
   - In `docs/TESTING.md` oder `AGENTS.md` einen kurzen Abschnitt ergänzen: wie die Chat-Pipeline
     ohne externen Anbieter geprüft wird (lokaler Mock hinter `OPENROUTER_BASE_URL` +
     signiertes `app_session_id`-Cookie + `JWT_SECRET`, wie AGENTS.md sie bereits beschreibt),
     und ausdrücklich vermerken, dass die heutige reale Route die Anbieter-Kette in
     `server/provider-endpoints.ts`/`agent-engine.ts` ist — **keine** neue Auswahl, **kein** zweiter
     Endpunkt. Falls die Leitprompt-Routenbeschreibung (`config/local-llm.env`) verbindlich wird,
     braucht sie ein eigenes, separater Review durchlaufendes Arbeitspaket (siehe Abschnitt 4).
   - Betroffene Datei: `docs/TESTING.md` (oder `AGENTS.md`). Risiko: niedrig (nur Doku).

**Explizit ausgeklammert:** Umbau der Provider-Kette, neue Abhängigkeiten, Änderungen an
Workflows/Secrets/`.env`, DB-Migrationen, Client-Verhaltensänderungen, `git commit/push`,
`gh`-Kommandos, Autofix über `pnpm format` auf das ganze Repo.

## 4. Offene Punkte / Entscheidungen (NICHT in diesem Sprint)

- **Modellroute:** Soll die Leitprompt-Vorgabe (`config/local-llm.env` + `docs/LOCAL-OFFLINE-LLM.md`,
  einzige lokale Route, kein Cloud-Ersatzweg) im Zielprojekt real eingeführt werden? Das ersetzt die
  bestehende Mehr-Anbieter-Kette und berührt `server/agent-engine.ts`,
  `server/provider-endpoints.ts`, `server/provider-guardian.ts`, `server/agent-router.ts` sowie alle
  Failover-Tests. Entscheidung + Freigabe des Repo-Owners nötig — konservativ **nicht** eigenmächtig umgebaut.
- **Lint-Lücke:** Kein `lint`-Script. Ob ESLint (oder nur `prettier --check`) als Gate ergänzt wird,
  ist eine Team-Entscheidung; in diesem Sprint wird nur per `pnpm format --check` bzw. an geänderten
  Dateien geprüft, falls verfügbar.
- **Release-Ablauf** (Git-Tag, APK-Bau, Neon-Migration) bleibt Owner- bzw. Deployment-Entscheidung
  (siehe `docs/RELEASE-CHECKLISTE.md`, `docs/SECURITY.md`).

## 5. Risiken

- `pnpm install` dauert und nutzt Node v24 gegen die geforderte Engine `>=22 <23` (nur Warnung laut AGENTS.md).
- Testlauf könnte fehlschlagen (z. B. Node-Engine, fehlende Env in Live-Tests). Live-Tests sind per
  Default übersprungen (`RUN_LIVE_*` nicht gesetzt) — ein Fehlschlag wäre dann echtes Signal, nur protokollieren.
- `.env.example`-Ergänzung darf niemals echte Werte aus der Umgebung kopieren — ausschließlich Namen/Platzhalter.
- Doku-Änderungen an AGENTS.md müssen die Testzahl nur nach einem grünen Lauf nennen (kein „Behaupten ohne Prüfen").
